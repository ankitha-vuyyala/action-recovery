# Introduction {#sec:intro}

An agent that acts on the world through tools inherits the oldest problem of distributed computing. It sent a request and no answer came back. The request may have been lost on the way; it may have been carried out with only the reply lost; or it may still be in flight and land a few seconds after the agent has given up. The three cases look identical to the agent (@fig:worlds). If the agent retries, it creates a second issue, a second e-mail or a second payment whenever the first attempt went through. If it does not, the task stays incomplete whenever the first attempt did not.

![Three worlds that give the agent the same observation. A request whose reply was lost, one that never arrived, and one that will commit after the agent has given up all end in the same timeout. Settle decides only after the in-flight bound $\Delta$ and the read lag $\lambda$ have passed, by counting the effects that carry the operation's tag.](fig_worlds.png){#fig:worlds width=80%}

The problem is as old as the two-generals argument [@akkoyunlu1975; @gray1978notes], and it has a standard engineering answer: give each logical operation a key and let the server execute each key at most once [@helland2012idempotence; @lee2015rifl; @doc_stripe]. Recent work shows that language-model agents run into exactly this problem and that the standard answer does not carry over by itself. Models frequently re-issue a write after an ambiguous failure without first checking whether it took effect [@sun2026didithappen; @gopnal2026idempotencybench]. Li [@li2026limbo] proves that no policy which only observes outcomes can be exactly-once while a request may still be in flight, and finds that idempotency keys remove most duplicates, but only on tools that honour them. Trofimov and Novikov [@trofimov2026anomalies] argue that without a primitive that yields one authoritative outcome, no recovery protocol is both safe under unknown outcomes and safe to compensate. Agent runtimes that add transactions [@mohammadi2026atomix; @chen2026cordon], durable execution [@doc_temporal; @doc_dbos] or rollback [@perera2026rac; @chang2025sagallm] reach exactly-once behaviour only when the downstream service honours a key or when failures are detectable, and neither holds for a lost reply.

How large is the gap that this leaves? I examined the documentation of 52 widely used write APIs across payments, developer tools, messaging and data services (@sec:census). Only {{cen.K|int}} of them offer a server-side key on the operation an agent would call, and most of those are payment APIs. Of these {{cen.K|int}} keys, {{cen.K.short|int}} are documented to expire within six hours or when the object's state changes. None of the twelve issue trackers and project tools and none of the thirteen messaging and mail services I examined offers one. These are services where many agent writes land and where a duplicate is visible to people. For these services, recovery without a key is not a corner case but the common case.

**The key observation.** Preventing a duplicate requires a key, but *repairing* one requires only that the client can tell which effects belong to which of its operations. Many key-less APIs persist a field that the client controls: an issue label or body, a mail header, a metadata map, a reference column, a custom property. If the client writes an operation id into that field, it can later count the effects of its own operation exactly. A search by content cannot do that, because other users may create records with the same content. With an exact count, the client can wait out the in-flight window, re-issue only if no effect exists, and remove any surplus copy it can prove is its own. In the census, {{cen.keyless.tag|int}} of the {{cen.keyless|int}} key-less APIs offer such a field together with a way to look it up, and {{cen.A|int}} of them offer an exact lookup. Payment engineers know this "client reference plus authoritative lookup" pattern informally. To my knowledge it has not been formalised for agents, compared against keys and workflow engines, or tested in the places where it must fail.

This paper makes four contributions.

1. **A theory of what recovery can achieve** (@sec:model, @sec:theory). I define *attributability* as the identifiability of the number of standing effects of an operation from what the client can observe. The notion unifies native keys, client tags, writer exclusivity and returned ids. I prove which guarantee each contract and read model admits. Without a known in-flight bound, prevention requires a durable key, and a key protects only within its retention. Convergence of the final state is achievable for attributable, reversible effects without any key; for irreversible effects it collapses to prevention. Content-based verification is unsound once look-alikes exist, aggregates are in general attributable only under exclusive writing, and the tag must survive a crash between dispatch and record. Finally, a policy that must stop at a horizon faces two indistinguishable worlds, so its residual risk is bounded below by the less likely of them. Settle's rule attains that bound when, given what it has seen, a late landing is less likely than a lost request. The result is an achievability map that predicts, cell by cell, where each recovery method must fail.
2. **A census of real API contracts** (@sec:census). I code 52 APIs from their official documentation and re-check a random sample in a second pass. The census places real services in the achievability map and measures the premise of the paper rather than asserting it.
3. **Settle, a recovery layer** that implements the constructive side of the theory (@sec:method). It writes each intent to a durable journal before dispatch, stamps an operation id into a persisted field, resolves unknown outcomes by that id after the read path's lag, and keeps reconciling up to a horizon. It compensates only effects it can prove are surplus, including effects the agent itself asks to delete, and reports *unknown* or an unrecoverable duplicate where nothing can be guaranteed.
4. **An internally pre-registered evaluation on real services with real faults** (@sec:setup, @sec:results). Six services run in containers: PostgreSQL, Gitea, Mailpit, Redis, SeaweedFS and TigerBeetle. Faults are injected at the network and process level and validated against each service's own records: lost replies, requests that never arrive, held connections, late commits with fixed and heavy-tailed delays, partial batches, transport redelivery and agent-process crashes. I compare sixteen conditions, namely ten baselines, Settle, four ablations of Settle and an outcome oracle, under a scripted agent and three OpenAI models. Grading uses service-side records only, and hypotheses, analysis code and source hashes were frozen internally before the first test episode. A second, separately frozen follow-up study of {{fu.n.all|int}} episodes adds the strongest tag-based alternative I could build, Settle without its implementation gaps, delayed redelivery, look-alikes from another account, plan-free intent binding and a frontier model (@sec:followup).

The evidence locates the boundary that the theory predicts. The scripted grid replays 1,188 worlds under fifteen conditions each ({{n.scripted|int}} episodes), and the language-model grid adds {{n.llm|int}} episodes. In ambiguous worlds whose write is attributable and reversible, Settle leaves {{h1.S.rate|pct}} of episodes inconsistent, against {{abs.best_rate|pct}} for the strongest baseline, a guard that waits exactly as long as Settle does. Without the two fault modes that every baseline fails by construction, redelivery and partial batches, the rates are {{rb.core.S|pct}} and {{rb.core.Gw|pct}}. Every remaining Settle failure is accounted for by the theory: either Settle's assumed in-flight bound was violated, whose consequence the theory bounds and which trades against latency, or the write lies in a cell where the theory admits no client-side guarantee. Durable keys, here those of a workflow engine, are exact where the service honours the key, but on key-less writes they are no better than plain retries ({{keyless.C4|pct}} for the workflow engine against {{keyless.C0|pct}} for plain retries). Verification by content, the basis of current client-side guards, fails in more than half of the worlds that contain same-account look-alike records. Language-model agents either re-issue blindly or check first. Checking helps, but it fails under look-alikes, after crash replay and under long delays: with my worst-case look-alikes and under long delays the observation itself is insufficient, and after a crash the framework re-issues before the model can check. With Settle underneath, all three models fall to {{llm.gpt-5.6-luna.S.hard|pct}} inconsistency in these hard worlds. Where nothing can be guaranteed, as with shared aggregates and redelivered e-mail, every method short of an outcome oracle fails, and Settle reports these cases instead of claiming success. The follow-up study draws the boundaries more tightly, including where they work against Settle. A tag-based wait-then-count policy is exactly as good as Settle on ordinary faults, so Settle's convergence pays off mainly for duplicates created by the transport. A content check with an author filter, combined with waiting out the bound, is as good as a tag when look-alikes come from another account. And the frontier model `gpt-5.6-sol` without a recovery layer leaves {{fu.f7.hard.C0|pct}} of hard worlds inconsistent, failing in the same cells as the smaller models, against {{fu.f7.hard.Snp|pct}} with Settle.
