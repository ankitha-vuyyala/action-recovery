# How common is each contract? A census of 52 APIs {#sec:census}

The theory makes the contract of a write, rather than the agent, decide what recovery can achieve. Whether this matters depends on how real services are distributed over the cells of @tbl:map_theory. I therefore coded the write contracts of 52 widely used APIs from their official documentation. The census is exploratory; it was coded after the test runs and was not pre-registered (@sec:setup).

**Sample and coding.** I chose APIs that agents are commonly connected to, in four domains of twelve to fifteen APIs each: payments and commerce, developer and project tools, messaging and e-mail, and CRM, data and cloud services. For each API I examined the *create* operation an agent would typically call (for example, creating an issue, sending a message, inserting a record or creating a payment) and recorded six properties from the vendor's documentation. The first is whether the operation accepts a client-supplied key that the *server* deduplicates, and for how long the key is retained. The second is whether a client-controlled field is persisted with the created object, such as a metadata map, an external id, a custom field, a header or a label. The third is whether objects can be retrieved by the exact value of that field. Lookups are coded as exact, as a search that the documentation describes as fuzzy or eventually consistent, as possible only by scanning a list of recent objects, or as impossible. The fourth is whether the field is hidden from end users. The fifth is whether the created effect can be undone through the API. The sixth is the URL of every documentation page relied on.

Each API receives a class from these properties: **K** if it has a server-side key; **A** if, without a key, it has a taggable field with an exact lookup; **A−** if the field can be found only through a lagged search or by scanning lists; and **C** if there is no usable field or no lookup at all. A second pass re-checked a random sample of {{cen.verify.n|int}} entries against the documentation, starting from the first pass's codes and sources. It confirmed all {{cen.verify.class_ok|int}} class assignments and found {{cen.verify.fact_errors|int}} factual error in a detail that did not affect the class (an additional search endpoint for one payment API). Twelve agreements out of twelve bound the class error rate only loosely, at about 25% with 95% confidence, so individual entries should be read with their sources. The full coded table, with documentation links, is part of the released artifacts, and @sec:censustable lists it.

**Keys are rare outside payments.** Only {{cen.K|int}} of the 52 APIs ({{cen.K.frac|pct0}}) have a server-side key on the examined operation (@fig:census). Eight of the twelve payment APIs have one; the other six are in the CRM, data and cloud group: Zendesk, Microsoft Graph calendar events, PagerDuty, and the conditional creates of S3, DynamoDB and Elasticsearch. None of the twelve developer and project tools and none of the thirteen messaging and e-mail services offers a key. Eleven key-less APIs have something *close to* a key, with weaker or undocumented guarantees: upserts on a client-chosen field (Salesforce, Airtable) without a documented concurrency guarantee; uniqueness constraints that reject a repeat with an error instead of returning the original outcome (Razorpay's order receipt, Confluence page titles, HubSpot's unique properties); client-chosen ids whose duplicate handling is undocumented (Linear) or whose collisions the provider explicitly does not guarantee to detect (Google Calendar); duplicate checks that last thirty seconds (Braintree) or minutes (Discord's nonce, SQS FIFO queues); and deduplication within one producer session (Kafka). An agent can build on several of these, but none is documented to give the guarantee of Proposition 1, and I do not count them as keys.

**Keys expire.** Retention is documented for most keys, and several are short. Mollie keeps keys for one hour, Zendesk for two and PayPal for six by default. PagerDuty's deduplication key lasts only while the alert is open, so a retry after it has been resolved opens a new incident. Square, Wise and Microsoft Graph do not document retention at all. By Proposition 1, a key protects only re-issues within its retention, and agents that resume after a crash, a deployment or a human approval can exceed one hour. Worse, {{cen.K.payments.listscan|word}} of the eight keyed payment APIs can find a payment by a client field only by scanning a list of recent payments, one (Adyen) offers no lookup at all, and one (Stripe) offers only an eventually consistent search. Once a key has expired, these APIs leave the client no exact way to attribute.

**Most key-less APIs are taggable.** Of the {{cen.keyless|int}} key-less APIs, {{cen.keyless.anyfield|int}} accept a client-controlled field with the write, and {{cen.keyless.tag|int}} ({{cen.keyless.tag.frac|pct0}}) persist one that can also be looked up. Of these, {{cen.A|int}} ({{cen.keyless.exact.frac|pct0}} of the key-less APIs) offer an exact lookup by the field, which makes them class A in the sense of @sec:theory; under a strict reading that treats Mailgun's events API and the Sent Items copy of Microsoft Graph mail as lagged, the count is {{cen.strict.A|int}}. For class-A APIs Proposition 2 applies as soon as the effect is reversible: {{cen.A.rev_full|int}} of the {{cen.A|int}} class-A operations can be undone through the API, and {{cen.A.rev_partial|int}} more only partly (GitHub's REST API closes rather than deletes an issue, and Notion moves a page to the trash). An exact lookup on GitHub needs the tag as a label, one per operation; a tag in the issue body can be found only through the lagged search index. Most of the remaining class-A operations send e-mail, which cannot be recalled, so Proposition 3 applies to them. Ten APIs are class A−. Jira's and Freshdesk's searches, for example, are documented as possibly missing recent writes (Freshdesk: for a few minutes), and Slack messages and Google Sheets rows can be found only by scanning recent items. Here attribution is possible, but only under a read lag $\lambda$ that is sometimes undocumented, or at the cost of a scan.

**A minority offers no attribution at all.** Class C, with no usable tag field or no lookup, covers {{cen.C|int}} APIs ({{cen.keyless.C.frac|pct0}} of the key-less ones): Microsoft Teams channel messages, Twilio SMS, Telegram, WhatsApp, Intercom conversations, Google Pub/Sub and standard SQS queues. Their writes cannot be tagged, or a tag cannot be looked up. Under a strict reading, which also moves Discord and Amazon SES to class C because their lookups depend on undocumented or sampled data, the share is {{cen.strict.C.frac|pct0}}. For class-C writes the theory leaves only safe abstention; waiting out a known in-flight bound tells the client that no attempt is still pending, but not whether one executed.

**Tags need not be visible.** A tag written into an issue body is visible to the people who read the issue. Among the {{cen.keyless.tag|int}} taggable key-less APIs, {{cen.tag.hidden|int}} offer a field the documentation describes as hidden from end users, for example Asana's external data, Shopify's metafields, Jira's issue properties, Postmark's and SendGrid's message metadata, and mail headers. Another {{cen.tag.visible|int}} offer only visible fields, such as GitHub labels or a Notion property, and for {{cen.tag.unclear|int}} the documentation does not say.

**What the census implies.** The census supports the premise of this paper on documentary evidence. Prevention by a server-side key is available for about a quarter of the APIs I examined and concentrated in payments. Convergence by attribution is available for most of the rest. Only a minority of services, mostly messaging services, leaves nothing but abstention. The census has limits. It covers documented behaviour, not behaviour under fault, and the sample is purposive rather than random. It codes one create operation per API, and several "unclear" entries could move with better documentation. The experiments that follow test whether the documented contract classes behave as the theory predicts, on real services and under real faults.
